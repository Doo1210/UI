# 智能体平台侧边栏信息架构设计方案二

> 方案名称：评测与观测独立方案  
> 版本：V1.1  
> 日期：2026-07-28  
> 适用范围：万悟工业智能体平台桌面端侧边栏

## 1. 方案概述

本方案在保留“运行中心”原有定位的基础上，将“智能体评测”和“智能体观测”合并为独立一级菜单“评测与观测”。

核心结构为：

```text
开发中心：负责智能体构建
评测与观测：负责智能体质量与表现分析
运行中心：负责智能体运行环境与镜像资产
```

本方案不将运行中心改名为“智能体运维”，原因是智能体运行时和镜像仓库并不完全属于智能体运维：

- 智能体运行时属于运行环境、部署和托管能力。
- 镜像仓库属于交付物和镜像资产管理能力。
- 智能体评测与观测关注智能体的质量、行为和执行表现。

三个模块分别回答：

| 一级菜单 | 核心问题 |
|---|---|
| 开发中心 | 智能体如何构建 |
| 评测与观测 | 智能体表现得怎么样 |
| 运行中心 | 智能体在哪里以及如何运行 |

## 2. 设计背景

平台现有能力包括：

- UniBot
- 智能体及共享资源广场
- 智能体开发与资源管理
- 事件中心
- 智能体运行时与镜像仓库
- 工业引擎（含视觉引擎）
- 平台运营
- 系统管理

后续将增加：

- 数字员工
- 智能体评测
- 智能体观测

平台用户同时区分：

- 系统管理员
- 组织管理员
- 其他用户

不同角色不仅拥有不同的菜单访问权限，统计分析等页面的数据范围也不同。

## 3. 设计目标

1. 保持开发、质量、运行三个业务域的边界清晰。
2. 将评测和观测放在一起，形成持续质量闭环。
3. 保留运行中心对智能体运行时和镜像仓库的准确表达。
4. 突出事件中心、工业引擎下的视觉引擎和智能体运行时等平台特色能力。
5. 尽量不修改已有二级菜单和页面结构。
6. 保持侧边栏最多两级，避免出现三级导航。
7. 支持按角色动态显示菜单，并独立控制数据范围。

## 4. 已确认的设计约束

1. 广场中的智能体、插件、MCP、技能和模型均为共享资源。
2. 开发中心的资源库用于管理用户创建、添加或引用的资源，与广场不冲突。
3. 端侧中心后续移除，本方案不再考虑。
4. 已有二级菜单不做大规模改名或重构。
5. 可以调整一级菜单名称、顺序、功能归属和视觉分组。
6. 运行日志、统计看板、扩缩容等与具体对象关联的功能，继续保留在详情页中。
7. API Key管理、统计分析、平台运营和系统管理固定在侧边栏下方。

## 6. 核心业务分区

如前端支持不可点击的弱分组标题，可以采用：

```text
智能应用
  UniBot
  数字员工
  广场

智能体工程
  开发中心
  评测与观测
  运行中心

  事件中心

```

分组标题只用于视觉区隔，不形成新的导航层级。

如暂时不支持分组标题，保持第5章的菜单顺序即可。

## 7. 开发中心定位

开发中心负责智能体的构建与资源管理：

```text
开发中心
├─ 智能体开发
└─ 资源库
```

核心职责包括：

- 创建单智能体、多智能体、工作流智能体和对话流智能体。
- 配置技能、组件、知识、记忆、模型、提示词和安全护栏。
- 管理用户创建或添加的开发资源。
- 提供调试、版本管理和发布入口。

智能体评测不再作为开发中心的固定二级菜单，但智能体开发详情页应提供“去评测”快捷入口。

## 8. 评测与观测定位

### 8.1 导航结构

```text
评测与观测
├─ 智能体评测
└─ 智能体观测
```

该模块关注智能体的质量、行为、性能和线上表现。

### 8.2 智能体评测

智能体评测主要包括：

- 测试集管理
- 批量运行
- 自动指标评分
- 人工评审
- 模型、提示词和版本对比
- 回归测试
- 发布质量门禁
- 线上问题样本复测

### 8.3 智能体观测

智能体观测主要包括：

- 会话和任务追踪
- Trace调用链
- 工作流节点执行过程
- 模型、技能、工具和MCP调用详情
- Token、时延和成本
- 异常、失败和重试分析
- 用户反馈
- 运行告警

### 8.4 评测与观测闭环

```text
开发智能体
→ 离线评测
→ 发布上线
→ 在线观测
→ 发现异常会话或Trace
→ 加入评测集
→ 回归评测
→ 优化并再次发布
```

评测和观测放在一起，可以共享：

- Trace与会话数据
- 测试集和异常样本
- 指标体系
- 模型及版本信息
- 用户反馈
- Token、时延和成本数据

### 8.5 上下文快捷入口

评测与观测拥有独立正式入口，但其他页面应提供上下文跳转：

- 智能体开发详情：“去评测”，自动带入当前智能体及版本。
- 已发布智能体：“查看观测”，自动筛选当前智能体。
- 运行时实例：“查看调用链”。
- 观测异常Trace：“加入评测集”。
- 评测结果：“返回修改智能体”或“发布该版本”。

## 9. 运行中心定位

运行中心保留原有名称和职责：

```text
运行中心
├─ 智能体运行时
└─ 镜像仓库
```

### 9.1 智能体运行时

负责：

- 智能体容器化运行环境
- Kubernetes部署与实例管理
- Pod状态
- 自动扩缩容
- 资源配额
- 环境变量
- API网关暴露
- 基础设施运行日志

### 9.2 镜像仓库

负责：

- 智能体镜像管理
- 镜像版本
- 镜像推送和拉取
- 安全扫描结果
- 运行时部署镜像选择

### 9.3 与评测和观测的边界

| 功能 | 关注对象 |
|---|---|
| 智能体评测 | 智能体输出质量和版本表现 |
| 智能体观测 | 会话、Trace、调用链和业务异常 |
| 智能体运行时 | Pod、容器、扩缩容和资源 |
| 镜像仓库 | 镜像资产及版本 |

运行中心解决“运行基础设施”，评测与观测解决“智能体表现”，两者不合并。

## 10. 数字员工定位

数字员工是智能体经过角色化和工作化包装后的业务应用，拥有持续存在的人设、职责、工作空间、任务、记忆、技能、工具、MCP和IM渠道。

第一阶段由一级菜单“数字员工”直接进入专家列表：

```text
数字员工 → 专家列表
```

专家详情继续使用页面内页签：

```text
人设｜工作空间｜任务｜记忆｜技能｜工具｜MCP｜IM渠道
```

当出现跨专家任务、协作或排班后，再演进为：

```text
数字员工
├─ 专家
├─ 任务中心
└─ 协作记录
```

## 11. 日志和统计边界

| 模块 | 数据范围 |
|---|---|
| 智能体观测 | 会话、调用链、模型、工具、Token和业务异常 |
| 智能体运行时 | 容器、Pod及基础设施运行日志 |
| 事件中心 | 事件触发、路由和任务执行记录 |
| 视觉引擎 | 视频任务、视觉告警和处置记录 |
| 运营看板 | 用户、内容、广场和资源运营情况 |
| 统计分析 | 应用、模型、API及Token的平台用量 |

统计分析属于跨模块通用用量数据，不放入运行中心或评测与观测。

## 12. 底部固定入口与角色权限

### 12.1 权限矩阵

| 功能 | 系统管理员 | 组织管理员 | 其他用户 |
|---|---|---|---|
| 统计分析 | 全平台范围 | 本组织范围 | 仅本人范围 |
| API Key管理 | 按平台授权范围 | 按组织策略 | 仅本人Key |
| 平台运营 | 全部功能 | 不可访问 | 不可访问 |
| 组织管理 | 全部组织 | 当前组织 | 不可访问 |
| 平台配置 | 可访问 | 不可访问 | 不可访问 |
| OAuth密钥管理 | 可访问 | 不可访问 | 不可访问 |

### 12.2 系统管理员

```text
API Key管理
统计分析
平台运营  >
系统管理  >
```

### 12.3 组织管理员

```text
API Key管理
统计分析
系统管理
```

### 12.4 其他用户

```text
API Key管理
统计分析
```

无权限入口直接隐藏，不显示禁用状态，也不保留空白位置。

### 12.5 统计分析的数据范围

系统管理员：

```text
全平台｜指定组织｜指定用户
```

组织管理员：

```text
本组织｜指定用户｜我的数据
```

其他用户固定为：

```text
我的数据
```

普通用户不显示范围选择器，页面明确显示“数据范围：仅本人”。数据范围必须由后端校验。

## 13. 平台运营与系统管理交互

### 13.1 二级菜单

```text
平台运营
├─ 审核工作台
├─ 广场治理
└─ 运营看板

系统管理
├─ 组织管理
├─ 平台配置
└─ OAuth密钥管理
```

### 13.2 推荐交互

点击平台运营或系统管理后，在主侧边栏右侧打开二级功能浮层：

```text
点击一级入口
→ 打开二级功能浮层
→ 选择功能并跳转
→ 关闭浮层
```

浮层规范：

- 建议宽度240至280px。
- 通过点击触发，不使用悬停触发。
- 再次点击、点击外部或按Esc关闭。
- 当前二级页面高亮，对应一级入口保持选中。
- 内容超高时浮层内部滚动。

组织管理员在系统管理下只有“组织管理”一个可见功能，可以直接进入组织管理，不显示箭头和单项浮层。

## 14. 工业引擎与视觉引擎

工业引擎确定为一级菜单，视觉引擎作为其二级菜单：

```text
工业引擎
└─ 视觉引擎
```

视觉引擎内部的视频与设备、算法、监管任务和告警等功能通过页面内页签或局部导航承载，不形成第三级侧边栏。

工业引擎为后续其他工业能力预留扩展空间：

```text
工业引擎
├─ 视觉引擎
└─ 其他工业引擎能力（未来）
```

新增二级能力应具备独立业务对象、独立工作区和长期扩展需求。
## 15. 一级菜单名称选择

### 15.1 推荐：评测与观测

优点：

- 直接表达两个现有功能。
- 用户不需要理解“运营”或“质量”的抽象含义。
- 不会与平台运营混淆。
- 不会错误包含智能体运行时和镜像仓库。

缺点：

- 未来加入会话运营、数据标注和A/B实验后，名称覆盖范围可能不足。

### 15.2 备选：智能体质量

适合未来扩展：

```text
智能体质量
├─ 智能体评测
├─ 智能体观测
├─ 质量看板
├─ 问题样本
└─ 告警规则
```

缺点是名称相对抽象，新用户不一定能立即判断其中包含调用链观测。

### 15.3 备选：智能体运营

仅在未来还将增加以下功能时考虑：

- 会话记录
- 用户反馈
- 数据标注
- A/B实验
- 质量分析

该名称与底部“平台运营”较接近，需要通过对象和视觉分区避免混淆。

### 15.4 不推荐：运营运维

“运营”和“运维”对应不同职责，组合后范围过大，也容易与“平台运营”混淆。

## 16. 方案优势与代价

### 16.1 优势

- 保留运行中心准确、稳定的产品定位。
- 评测和观测形成完整质量闭环。
- 开发、质量、运行三个领域边界清晰。
- 不需要将镜像仓库解释成智能体运维。
- 评测与观测作为长期核心能力具有足够可见性。
- 一级菜单数量增加有限，端侧中心移除后仍可接受。

### 16.2 代价

- 上方核心业务区增加一个一级菜单。
- 开发人员进行评测时需要跨一级模块，但可通过上下文快捷入口解决。
- 初期只有两个二级功能时，独立一级菜单的内容密度相对较低。
- 后续功能扩大后可能需要将“评测与观测”改名为“智能体质量”或“智能体运营”。

## 17. 与方案一的主要差异

| 对比项 | 方案一 | 方案二 |
|---|---|---|
| 智能体评测 | 开发中心下 | 评测与观测下 |
| 智能体观测 | 运行中心下 | 评测与观测下 |
| 运行中心 | 运行时、镜像、观测 | 仅运行时、镜像 |
| 一级菜单数量 | 较少 | 增加一个 |
| 评测观测闭环 | 分散 | 集中 |
| 运行中心语义 | 部分混合质量观测 | 聚焦运行基础设施 |

## 18. 调整清单

### 本期建议

- 新增一级菜单“数字员工”，直接进入专家列表。
- 新增一级菜单“评测与观测”。
- 在评测与观测下设置“智能体评测”和“智能体观测”。
- 开发中心保持“智能体开发、资源库”。
- 运行中心保持“智能体运行时、镜像仓库”。
- 移除端侧中心。
- 保留工业引擎为一级菜单，将视觉引擎调整为其二级菜单。
- 将API Key管理和统计分析作为底部固定一级菜单。
- 将平台运营和系统管理固定在侧边栏底部。
- 平台运营和系统管理点击后打开二级功能浮层。
- 根据角色控制菜单和数据范围。

### 后续演进

- 为智能体开发、发布和运行页面增加评测与观测快捷入口。
- 建立“异常Trace加入评测集”的质量闭环。
- 评测与观测功能扩大后，评估是否改名为智能体质量或智能体运营。
- 管理模块超过6个二级功能时，将浮层升级为可固定的右侧二级侧边栏。

## 19. 最终结论

方案二最终结构为：

```text
开发中心
├─ 智能体开发
└─ 资源库

评测与观测
├─ 智能体评测
└─ 智能体观测

运行中心
├─ 智能体运行时
└─ 镜像仓库
```

该结构不套用宽泛的“运营运维”概念，而是明确区分智能体构建、智能体质量和运行基础设施。它比将评测与观测拆开放置更利于形成持续质量闭环，也避免破坏运行中心现有功能的准确归属。
