# 智能体平台侧边栏信息架构设计方案

> 版本：V1.2  
> 日期：2026-07-28  
> 适用范围：万悟工业智能体平台桌面端侧边栏

## 1. 背景与目标

平台现有智能体使用、共享资源获取、智能体开发、事件驱动、运行托管、视觉分析、平台运营及系统管理等能力，后续还将增加：

- 智能体评测
- 智能体观测
- 数字员工（当前产品形态为“专家”）

平台用户区分系统管理员、组织管理员和其他用户。不同角色不仅拥有不同的菜单访问权限，统计分析等页面的数据范围也不同。

本方案目标：

1. 体现平台以智能体为核心的产品定位。
2. 突出事件中心、智能体运行时和工业引擎下的视觉引擎等特色能力。
3. 容纳智能体评测、智能体观测和数字员工等后续功能。
4. 尽量保留现有二级菜单和页面结构。
5. 让普通用户能够直接访问统计分析和API Key管理，同时避免向其暴露管理菜单。

## 2. 已确认的设计约束

1. 广场中的智能体、插件、MCP、技能和模型均为平台共享资源，“广场”的名称和定位保持不变。
2. 开发中心的“资源库”用于管理用户创建、添加或引用的资源，与共享广场不冲突。
3. 端侧中心将在后续版本移除，本方案不再考虑。
4. 已有二级功能菜单不做大规模改名或重构。
5. 可以调整一级菜单名称、顺序、功能归属和视觉分组。
6. 与具体对象关联的配置、日志、统计优先保留在详情页页签中。
7. 系统管理员可以访问平台运营和系统管理下的全部二级功能。
8. 组织管理员可以访问统计分析、组织管理和API Key管理。
9. 其他用户可以访问统计分析和API Key管理。
10. 统计分析使用统一页面，数据范围根据角色控制。

## 3. 信息架构原则

### 3.1 一级菜单代表稳定业务域或独立入口

一级菜单用于进入完整业务领域、工作中心或所有用户均可访问的独立工具。低频管理能力与核心业务能力应在视觉上分离。

### 3.2 二级菜单代表稳定业务对象

智能体开发、资源库、事件接入、事件任务、智能体运行时和镜像仓库等适合作为二级菜单。运行日志、统计看板、扩缩容配置等继续保留在详情页内。

### 3.3 最多保持两级导航

侧边栏允许“工业引擎—视觉引擎”两级导航。视觉引擎内部的视频设备、算法、监管任务和告警等能力通过页面内导航承载，不继续拆成第三级侧边栏。

### 3.4 菜单权限与数据权限分离

| 权限层 | 控制内容 |
|---|---|
| 菜单权限 | 是否显示入口、是否允许进入页面 |
| 操作权限 | 是否可以创建、编辑、导出、禁用或删除 |
| 数据权限 | 可以查看本人、本组织还是全平台数据 |

数据范围必须由后端校验，不能只依赖前端隐藏菜单或筛选项。

## 4. 推荐侧边栏结构

侧边栏采用“上方核心业务区＋下方固定工具与管理区”。

### 4.1 上方核心业务区

```text
UniBot
数字员工
广场
├─ 智能体广场
├─ 插件广场
├─ MCP广场
├─ 技能广场
└─ 模型广场

开发中心
├─ 智能体开发
├─ 资源库
└─ 智能体评测（新增）

事件中心
├─ 事件接入
└─ 事件任务

工业引擎
└─ 视觉引擎

运行中心
├─ 智能体运行时
├─ 镜像仓库
└─ 智能体观测（新增）
```

### 4.2 下方固定区

```text
API Key管理
统计分析
平台运营  >
系统管理  >
```

- API Key管理：一级菜单，直接进入。
- 统计分析：一级菜单，直接进入。
- 平台运营：一级入口，点击打开二级功能浮层。
- 系统管理：一级入口，点击打开二级功能浮层。

### 4.3 布局结构

```text
顶部品牌区：固定
中部业务菜单：独立滚动
底部工具与管理区：固定
```

底部四项预计占用约200至220px高度。在低高度窗口中，仅中部业务菜单滚动，底部入口不得覆盖业务菜单。

## 5. 数字员工

数字员工是智能体经过角色化、工作化包装后的业务应用，具有持续存在的人设、职责、工作空间、任务、记忆、技能、工具、MCP和IM渠道，不属于普通开发资源或共享广场。

第一阶段由一级菜单“数字员工”直接进入专家列表，不增加只有一个子项的展开层级：

```text
数字员工 → 专家列表
```

专家详情继续使用页面内页签：

```text
人设｜工作空间｜任务｜记忆｜技能｜工具｜MCP｜IM渠道
```

当出现跨专家任务管理、协作或排班后，再演进为：

```text
数字员工
├─ 专家
├─ 任务中心
└─ 协作记录
```

## 6. 智能体评测

智能体评测放入开发中心：

```text
开发中心
├─ 智能体开发
├─ 资源库
└─ 智能体评测
```

它主要服务“开发—调试—评测—发布”链路，可包含测试集、批量运行、指标评分、版本对比、模型与提示词对比、人工评审和发布门禁。

## 7. 智能体观测

将“部署运行”改名为“运行中心”，并加入智能体观测：

```text
运行中心
├─ 智能体运行时
├─ 镜像仓库
└─ 智能体观测
```

| 功能 | 关注层级 | 典型内容 |
|---|---|---|
| 智能体运行时 | 基础设施和容器层 | Pod、容器、扩缩容、资源配额、环境变量 |
| 智能体观测 | 智能体执行和业务调用层 | 会话、Trace、工作流、模型、工具、Token、异常 |

智能体观测可包含调用链、工作流节点、模型与工具调用、Token、时延、成本、会话追踪、异常分析和告警。

## 8. 日志和统计边界

| 模块 | 数据范围 |
|---|---|
| 智能体观测 | 调用链、工作流、模型、工具、Token和业务异常 |
| 智能体运行时 | 容器、Pod及基础设施运行日志 |
| 事件中心 | 事件触发、路由和任务执行记录 |
| 视觉引擎 | 视频任务、视觉告警和处置记录 |
| 运营看板 | 用户、内容、广场和资源运营情况 |
| 统计分析 | 应用、模型、API及Token的平台用量 |

统计分析属于跨模块通用用量数据，不放入运行中心。事件任务的运行日志和统计看板继续保留在任务详情页中。

如允许微调菜单文案，侧边栏可以显示“用量统计”，页面标题保留“统计分析”；如需保持现有名称，则统一使用“统计分析”。

## 9. 固定底部入口

### 9.1 API Key管理

API Key管理作为所有角色可见的一级菜单，直接进入页面，不设置下级菜单。放在底部工具区可以提供快速入口，同时不干扰核心业务主线。

只有未来形成API文档、SDK、OAuth应用、接入调试等完整能力后，才考虑建立“开放平台”。

### 9.2 统计分析

统计分析作为所有角色可见的一级菜单，直接进入统一页面。不同角色使用相同路由，通过权限控制数据范围。

### 9.3 平台运营

平台运营仅系统管理员可见：

```text
平台运营
├─ 审核工作台
├─ 广场治理
└─ 运营看板
```

### 9.4 系统管理

```text
系统管理
├─ 组织管理
├─ 平台配置
└─ OAuth密钥管理
```

- 系统管理员可访问全部功能。
- 组织管理员只可访问组织管理。
- 其他用户不显示系统管理。

API Key管理和统计分析均从系统管理移出。

## 10. 角色权限与数据范围

### 10.1 权限矩阵

| 功能 | 系统管理员 | 组织管理员 | 其他用户 |
|---|---|---|---|
| 统计分析 | 全平台范围 | 本组织范围 | 仅本人范围 |
| API Key管理 | 按平台授权范围 | 按组织策略 | 仅本人Key |
| 平台运营 | 全部功能 | 不可访问 | 不可访问 |
| 组织管理 | 全部组织 | 当前组织 | 不可访问 |
| 平台配置 | 可访问 | 不可访问 | 不可访问 |
| OAuth密钥管理 | 可访问 | 不可访问 | 不可访问 |

### 10.2 各角色底部菜单

系统管理员：

```text
API Key管理
统计分析
平台运营  >
系统管理  >
```

组织管理员：

```text
API Key管理
统计分析
系统管理
```

其他用户：

```text
API Key管理
统计分析
```

无权限入口直接隐藏，不显示禁用状态，也不保留空白位置。

### 10.3 统计分析范围

系统管理员：

```text
全平台｜指定组织｜指定用户
```

组织管理员：

```text
本组织｜指定用户｜我的数据
```

其他用户：

```text
我的数据
```

普通用户不显示范围选择器，页面明确显示“数据范围：仅本人”。

### 10.4 API Key安全规则

- 普通用户管理自己的API Key。
- 组织管理员是否管理组织成员Key，由组织安全策略决定。
- 系统管理员按照平台安全策略管理授权范围内的Key。
- 完整密钥只在创建时展示一次。
- 管理员只能查看名称、归属、创建时间、末尾字符、状态和最近使用时间，不能重新查看完整密钥。
- 创建、禁用、撤销和轮换均写入审计日志。

## 11. 管理入口的二级导航交互

### 11.1 方案选择

| 方案 | 适用情况 | 本期建议 |
|---|---|---|
| 点击后打开浮层 | 二级菜单3至5项、使用频率较低 | 推荐 |
| 右侧二级侧边栏 | 二级菜单较多、管理员频繁切换 | 后续可升级 |
| 页面多Tab | 功能属于同一对象且共享上下文 | 不推荐 |

审核工作台、广场治理、运营看板、组织管理、平台配置和OAuth密钥管理都是独立页面，不适合用同一页面的Tab承担全局导航。

### 11.2 浮层交互

```text
点击“平台运营”或“系统管理”
→ 在主侧边栏右侧打开二级功能浮层
→ 选择功能并跳转
→ 关闭浮层
```

浮层建议：

- 宽度240至280px。
- 点击触发，不使用悬停触发。
- 再次点击、点击外部或按Esc关闭。
- 当前二级页面高亮，对应一级入口保持选中。
- 内容超高时在浮层内部滚动。
- 主侧边栏收起后，通过一级图标继续打开浮层。

组织管理员在系统管理下只有“组织管理”一个可见功能，可直接进入组织管理，不显示箭头和单项浮层。系统管理员拥有多个功能时，显示箭头并打开浮层。

## 12. 工业引擎与视觉引擎

工业引擎作为一级菜单，承载面向工业场景的多类引擎能力；视觉引擎作为当前首个二级能力：

```text
工业引擎
└─ 视觉引擎
```

视觉引擎内部的视频与设备、算法、监管任务和告警等功能通过页面内页签或局部导航承载，不继续拆成第三级侧边栏。

后续增加其他工业能力时，可以继续扩展同级菜单：

```text
工业引擎
├─ 视觉引擎
└─ 其他工业引擎能力（未来）
```

新增二级能力应满足独立业务对象、独立工作区和长期扩展需求，避免将单个配置页面提升为二级菜单。
## 13. 智能体质量的后续演进

现阶段将智能体评测放入开发中心、智能体观测放入运行中心。当两者成为跨平台独立能力，拥有独立项目、数据集、权限和告警体系后，再考虑：

```text
智能体质量
├─ 智能体评测
└─ 智能体观测
```

## 14. 调整清单

### 本期建议

- 新增一级菜单“数字员工”，直接进入专家列表。
- 在开发中心新增“智能体评测”。
- 将“部署运行”改名为“运行中心”。
- 在运行中心新增“智能体观测”。
- 移除端侧中心。
- 保留工业引擎为一级菜单，将视觉引擎调整为其二级菜单。
- 将API Key管理和统计分析移出系统管理，作为固定底部一级菜单。
- 将平台运营和系统管理固定在侧边栏底部。
- 平台运营和系统管理点击后打开二级功能浮层。
- 根据角色过滤菜单，并控制统计分析的数据范围。

### 本期保持不变

- 广场及其现有二级菜单。
- 开发中心现有的智能体开发和资源库。
- 事件中心的事件接入和事件任务。
- 事件任务详情中的任务配置、运行日志和统计看板。
- 智能体运行时详情中的扩缩容、资源配额和环境变量。
- 视觉引擎现有页面功能和页签。

### 后续演进

- 数字员工出现跨专家任务和协作后，再展开二级菜单。
- 评测和观测成为跨平台能力后，再考虑建立智能体质量。
- 管理模块超过6个二级功能或需要频繁切换时，将浮层升级为可固定的右侧二级侧边栏。
- API能力形成完整体系后，再考虑建立开放平台。

## 15. 最终结论

```text
上方：UniBot、数字员工、广场、开发中心、事件中心、工业引擎、运行中心

下方固定：
API Key管理：所有角色可见，直接进入
统计分析：所有角色可见，直接进入，数据范围按角色控制
平台运营：仅系统管理员可见，点击打开二级功能浮层
系统管理：系统管理员和组织管理员按权限可见
```

本方案在基本保留现有二级菜单的前提下，通过新增数字员工、调整一级菜单名称、固定通用入口并引入角色化权限控制，使侧边栏能够同时表达平台核心能力、工业场景特色和清晰的管理边界。
