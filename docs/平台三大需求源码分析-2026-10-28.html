总体判断

三项需求共同涉及访问控制，但不应共用一个“公开/私密”开关。

源码带来的三个修正

需求一不是从零补版本：智能体已有快照，已发布聊天和 Web URL 已按 App.Version 查指定快照。真正需要拆开的是：版本发布和广场审核目前走同一条流程。

需求二不是全平台完全没有共享：知识库已有真实成员授权，Skill 也有广场领取关系；但它们不等于应用和各类开发资源共用的协作者权限体系。

需求三不是从零重写侧栏：动态菜单已经有 DRILL_DOWN 专属侧栏、外部跳转和 qiankun。还存在洞察能力的组织开通状态，可参考其生命周期，但不是通用外部平台开通服务。

改造难度的相对判断

发布/上架拆分：中高。UI 入口较直接，难点是现有运行权限、凭证、审核、广场查询和历史统计都引用发布概念。

共享：高。涉及列表数据范围、每个读写入口、资源依赖、执行身份、撤权与跨服务一致性，是三项中覆盖面最大的部分。

平台集成：首个平台中高，后续取决于外部系统。首页和专属侧栏较易；身份映射、组织开通、服务端鉴权及失败恢复才是主要成本。未做接口盘点和部署验证，不据此给出人天承诺。

发布与上架

发布生成可服务的版本；上架分发某个已发布版本。广场下架不应停止外部服务。

当前链路

前端 publishAppDialog 同时收集 public/organization/private 范围、广场标签、版本号和版本描述；agent/form.vue 把 scope 转为 publishType，调用 appspace/app/publish。

BFF PublishApp 在命中广场审核时，仅创建审核单；智能体先冻结提交快照。审批通过后 publishAppCore 再执行版本生效及 app-service 发布登记。无需审核时则直接创建各业务版本并记录广场治理。

app-service 的 App 记录同时包含 AppID、AppType、UserID、OrgID、PublishType、Version 和广场分类字段。广场查询与已发布应用访问检查都使用 PublishType，因此它承担了服务可用、可见范围和广场供给的多重含义。

已发布智能体聊天、Web URL 按 App.Version 获取快照，是稳定版本路由的可复用基础。工作流、RAG、事件、Skill 各有不同版本发布适配，不能只修改智能体一个分支。

不能直接复用“取消发布”作为下架

当前 app-service UnPublishApp 会删除其他用户的旧应用级 ApiKey 记录，再删除 App 发布关系及相应历史/收藏关系；BFF 对工作流还调用 AssistantWorkFlowDeleteByWorkflowId 清理绑定。这里说的是该旧应用凭证表路径，不能推断所有新版用户级 API Key 都会被删除。

所以新增广场下架应只改变 listing 状态并保留审计记录。它不应删除稳定版本、停止 API/Web URL、清理开发引用或撤销用户已有的独立共享授权。历史收藏可保留并显示“已下架”。

另设“停用对外服务”：阻止新运行并按规则处理活动任务、URL 和凭证；若仍在广场上架则同步隐藏/禁用试用。停用不等于删除版本和历史。

建议的状态与版本规则

  • 工作草稿可持续修改；只有显式发布才产生不可变 Release，并在发布成功后切换服务生效指针。数据库提交或某个下游失败时，不提前宣称发布成功。
  • 上架状态与审核状态分开。已有 v1 上架且 v2 审核中时，广场仍展示并运行 v1；审核驳回不影响旧条目或 API。
  • 默认建议：API/Web 当前稳定版本与广场已审核版本分别绑定。API 可先升级 v2，广场保留曾发布且仍可服务的 v1，审核后才切 v2。每次广场试用必须明确传递并校验 listedVersionId，不能继续无条件读 App.Version。
  • 如果产品要求广场必须始终使用“当前唯一稳定版本”，则需要在发版时联动重新审核/暂停展示，或限制生效时机。该规则与“审核前广场保持旧版”不能同时无条件成立，需在详细设计阶段定稿。
  • 回滚改变渠道指针而不是修改历史快照。新会话默认使用当前绑定版本，已有会话是否保留原版本要明确；建议会话/执行记录保存版本 ID，避免一次任务混用两个版本。
  • 版本快照还需记录依赖引用和凭证绑定方式。固定 Agent 配置不代表知识内容、模型服务或外部工具结果都被永久冻结。版本化依赖固定版本；动态知识和外部系统明确更新规则、权限与健康检查。

前端如何呈现

开发页提供三个独立入口：“发布版本”“共享”“上架广场”。发布弹窗只收版本和说明；上架弹窗选择已发布版本、范围、分类与展示内容，审核开启时显示“提交上架”。

列表分别显示草稿有改动/当前服务版本、服务启停、广场版本和审核状态。例如“服务 v2 · 已上架 v1 · v2 待审核”，避免一个“已发布”标签掩盖状态差异。

广场页面由 Listing 驱动，不再把所有已发布 App 自动当作广场条目。public/organization/private 的旧值先迁为明确的运行访问范围；广场范围另外迁移，私密应用默认不进入公共广场。

应用与资源共享

将“使用成品”和“共同开发”区分。允许编辑草稿，不应自动获得发布、上架、转授权或查看密钥的权力。

现有基础与缺口

已发布应用访问检查按 public/organization/private 判断；没有在这条检查链中查询指定用户的对象授权，因此定向共享需要新的授权入口。

智能体 GetAssistant/GetAssistantList 使用 DataPerm(userID, orgID)，草稿聊天也明确携带当前身份。共享后不只需要列表多一行，还要让详情、保存、调试、工具配置、版本读取和删除等入口逐项执行操作授权。不能通过把请求者换成作者或传空 userId 来绕过隔离。

知识库 KnowledgePermission 已有按知识库 + 用户 + 组织的成员记录，以及查看 0、编辑 10、授权 20、系统管理 30。应先保留并适配，避免新建另一套知识库权限产生冲突。已有“查看”不保证等同于新的“仅可检索/引用”，尤其原始文档访问和导出须单独核验。

Skill 的 ShareSquareSkill 实际创建 AcquiredSkill 领取关系；领取、收藏、复制、共同编辑是不同关系，不能因接口名有 share 就当作定向协作。

可使用运行已发布版本、访问自己的会话按类型引用/调用/检索已授权资源编辑配置、查看敏感配置、复制导出、发布上架、转授权

内部建议用 use/run、read_config、edit_config、debug、publish、list、manage_share、delete 等能力表达，再映射成两档 UI；不要把所有权限永久压成一个可无限比较的数字。若编辑者确需发布，可显式增加发布能力。

应用“可使用”默认针对成品。未发布草稿不因为勾选“可使用”就成为对外服务；若需要协作者试运行草稿，应定义独立调试授权。

资源类型不同，动作不能一刀切：模型对应推理和配额，MCP/工具对应调用与连接配置，知识对应检索/文档访问，Skill 对应引用与源文件编辑，提示词对应引用与内容编辑。资源可用授权不自动开放底层管理页面。

统一授权的最小方案

定义 AssetGrant：ownerOrgId、assetType、assetId、subjectType、subjectId、subjectOrgId、capabilities、grantor、有效期、撤销状态。身份复用 IAM；授权策略集中管理，各业务通过适配层执行检查。初期可作为现有服务内模块，不必立刻拆出新微服务。

第一期建议只支持同组织指定用户，共享列表提供“我创建的/共享给我的”。如果要跨组织，必须显式记录资源归属组织与接受者组织，并检查双方关系、资源依赖和费用；不要把 publishType=public 当作跨组织协作。

角色权限决定能否使用某项平台功能，对象授权决定能操作哪个资产。共享资产不应迫使接受者获得全量开发资源访问权；可以提供受限的共享详情/工作区。

保存操作用草稿 revision 做乐观并发控制；两人编辑同一配置发生冲突时提示合并或刷新，第一期不必直接做多人实时协同。

运行、会话、审计均保留真实请求者和资源所有者；服务凭证与操作者身份分开。受权调用代理可以使用受管凭证，但不向共享者返回密钥原文。

最容易遗漏的依赖授权

A 把应用分享给 B，不应自动把 A 的知识库、模型密钥和工具管理权限也分享给 B。需要在发布或引用时检查：该资源是否允许这个应用作为受管运行主体使用。

建议对成品运行提供受约束的应用运行身份：只可调用版本中列出的依赖，记录真实调用者、用量归属和操作审计。消费应用不等于可以在自己的其他应用中复用其所有依赖。

开发协作中可直接共享资产引用；当编辑者修改依赖时，需要重新校验授权和凭证可用性。不能把共享应用内的引用当作通行证，跳过底层知识、工具或模型的检查。

撤权需要覆盖列表、详情、下载、调试、API、后台任务和缓存。建议阻止新调用并使授权缓存及时失效；既有运行是否终止按任务类型规定。被其他应用引用的资源撤权/删除时，先给出影响清单，再采用停用引用或受控迁移。

复制另存形成新资产，应有明确 copy/export 权限并重新绑定依赖与凭证；它不等于共同编辑原资产。用户私有会话、记忆、业务数据和运行日志不因配置共享自动开放。

首页与平台集成

已有导航和接入方式可以复用，新增重点是“平台目录 + 组织开通 + 用户授权”的统一判断。

源码已支持什么

BFF 的平台能力清单和 MenuOverlay 区分内部路由、目录及外部应用；navigationMode=DRILL_DOWN 已支持进入专属侧栏。前端 layout 有进入二级栏、返回主导航、根据当前路由恢复专属侧栏的逻辑。

外部菜单点击通过 GetMenuExternalLaunch 校验菜单权限并生成跳转 URL。qiankunUtil 已登记 bi-paas、et-engine，micro/sharedState 同步 token、userId 和 orgId。可复用这些集成模式，而不是所有外部平台都强制改成同一种前端。

现有 MenuOverlay 的 enabled/visible 是加载的菜单配置字段；menu.Trim 接收用户权限与管理员身份，不接收组织平台开通信息。因此菜单配置启用和租户开通是两个层次。

洞察组织模块已有 capabilities、pending/ready/failed/disabled、revision/appliedRevision 和重试机制，是开通流程的参考实现；需要通过通用平台目录和适配器推广，而不是把所有平台硬塞进洞察专用表。

建议提供平台目录查询、当前组织开通状态、申请/开通/停用和 launch 编排等接口。首页、菜单裁剪、外部 launch、网关及业务接口使用同一授权判断；路由守卫只负责用户体验，后端负责真正阻止访问。

接入路径按外部系统选

现有 external-launch 支持把原始 token 用参数模板放入跳转 URL。新接入第三方平台建议改用一次性短时 launch ticket 或标准 SSO 交换，再生成面向目标平台的会话，避免把主平台长期令牌作为通用 URL 参数。可信同域微前端的现有 token 通道需与第三方跨域接入分开评估。

开通成功必须以外部租户/功能实际就绪为准。复用洞察模块中可重试、幂等、持久化状态的思路，避免前端点一次“开通”就仅把 enabled=true 写入。

  • 纯跳转 + SSO：外部平台基本独立，主平台维护目录、开通和入口；适合第一期快速集成。
  • 微前端：需要保留主平台侧栏且子平台能够配合接入时，复用 qiankun；处理路由前缀、资源路径、组织切换、登录过期和卸载状态。
  • iframe：仅在对方允许嵌入且登录/Cookie/内容安全策略可配合时使用，不作为默认承诺。
  • 后端能力集成：把平台能力开放成工具、知识查询或工作流节点，另补能力元数据、受管身份、配额和审计。首页跳转不能替代这一层。

主平台与外部平台的责任

主平台负责身份、组织、平台目录、开通编排、统一入口和总体授权；外部平台负责专业业务、数据和执行。外部服务仍需核验可信身份、组织映射和功能授权，不能只信浏览器传来的 orgId。

第一期先选一个平台跑通完整链路，建议优先复用已存在的接入模式。后续按适配契约接入，不在首页组件里逐个平台堆判断。

实施顺序与验收

先拆状态和授权边界，再逐类接入资产；首页可以并行做展示，但不要先承诺所有平台已可用。

必须验证的业务场景

  • 已发布但未上架：授权 API/Web 可以运行，广场不可发现；发布失败不会切换生效版本。
  • 上架后下架：广场不可发现/试用，独立授权的外部调用继续工作；凭证、历史和应用依赖不因 delist 被误删。
  • v2 发版/待审核/驳回：API 与广场各自按已定义版本运行；审批成功只切目标版本，不能取审批时的当前草稿。
  • 两名协作者同时保存发生冲突；编辑者不能越权发布、删除、转授权或读取密钥；消费者不能访问配置接口。
  • 共享接受者能在列表看到资产、详情与实际操作权限一致；撤权后列表、深链接、下载、API 和新异步任务都不再放行。
  • 共享成品调用私有知识或工具：只在明确受管授权下运行，不向使用者自动开放底层资源和他人会话；用量记录真实调用者及扣费主体。
  • 组织 A 开通、组织 B 未开通：同账号切换组织时卡片、侧栏、launch、业务 API 一致变化；前端改路由不能绕过服务端。
  • 开通过程超时、外部平台失败、重试、停用、到期和权限撤回：状态可恢复、请求可拒绝、审计可追踪。

迁移与兼容

保留旧接口的兼容期。旧 public/organization 已发布记录可在核验后迁为启用的服务绑定与对应广场条目；private 默认仅迁为私有服务，不自动进入公共广场。依实际广场使用行为校验，不能仅凭表值批量认定授权。

待审核提交迁为 ListingSubmission，原有生效版本和可运行渠道保持不变。历史快照、业务版本、URL、旧应用 Key/新用户级 Key 的身份关系分别核对。

将“发布量”“上架量”“可用应用量”“共享人数/领取数”分别定义统计口径。先双读比对状态与访问结果，再逐步切换，避免广场列表、运营看板和实际调用互相矛盾。

跨服务写入（业务版本、发布关系、审核状态）不能只依赖本地事务，需设计幂等、状态中间态、失败补偿和对账；现有 app-service 本地事务只覆盖本服务记录，不代表整个发布链已具备分布式原子性。
